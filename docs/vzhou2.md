## Repository and Codebase Organization

The project is one Docker Compose stack. nginx sits in front and sends `/api` to a FastAPI backend and `/student`, `/staff` and `/admin` to three separate Vite/React apps, one per role. The backend talks to MySQL for everything relational and, since this project, to three model-serving containers that only it can reach: **Ollama** generates answers, **Infinity** computes embeddings, and **ChromaDB** stores the vectors.

Inside `backend/app/` the layers are strict:

- **`routers/`** is HTTP only: parse the request, check access with the dependencies in `common/`, call a service, return a schema. `rag.py` is the router we added (profiles, resources, uploads, jobs, health and compare).
- **`services/`** holds the logic. The existing `qa_service.py` owns questions and posts. Everything RAG is in `services/rag/`, split by job: `fetchers.py` and `ssrf.py` get content, `chunking.py`, `tokens.py` and `presets.py` split it, `citations.py` builds the link for every chunk, `embeddings.py` and `store.py` talk to Infinity and Chroma, `ingest.py` and `catalog.py` run ingestion jobs, `pipeline.py` does retrieval and prompting, `answer_job.py` posts the AI answer, and `locks.py` keeps generation to one call at a time.
- **`models/`** and **`schemas/`** are the SQLAlchemy tables and the Pydantic request and response shapes. Migration `002_rag.py` adds resources, ingestion profiles, jobs, the `AI` author role and `questions.ai_status`.
- **`tests/unit/`** tests the services with their collaborators patched, and **`tests/integration/`** runs against the live stack. **`eval/`** holds the course's comparison harness, its ground truth and sample data.

**How a question becomes a cited answer.** Before any question is asked, staff register resources (syllabus, schedule, a GitLab repository, uploads; the historical-Q&A resource is created automatically per course). An ingestion job fetches each one, splits it by structure (HTML headings, markdown headings, PDF pages, one thread per Q&A chunk), falls back to a sliding window or a semantic chunker when a piece is still too long, embeds the chunks through Infinity and stores them in Chroma. Each chunk's metadata already contains its finished citation: a GitLab blob link with line numbers for markdown, a page anchor for PDFs, or a `#:~:text=` fragment for web pages. Computing the link at ingest time means the model never writes a URL, so it cannot invent one.

Then a student posts a question. `routers/qa.py` commits the `Question` through `qa_service`. If the live board is on (`RAG_LIVE_ENABLED`) and the course is under its pending cap, `answer_job.initial_status` marks it `PENDING` and FastAPI runs `answer_job.run` as a background task, so the student's request returns immediately. The job copies what it needs into a plain snapshot (the ORM session is gone by then), and `pipeline.retrieve` embeds the title and body with the course's default profile, asks Chroma for the top K chunks and keeps those at or above the similarity threshold. No chunk left means `NO_MATCH` and no post. Otherwise the job waits for the generation lock, builds a prompt with the chunks inside tags and the guardrail system prompt, and calls Ollama. If the reply is a decline (`decline.py`) the status is `DECLINED`. If not, `create_ai_answer` locks the question row, checks it is still open, and inserts an ANSWER post written by the system AI user with `author_role = AI`, the citations from the chunk metadata and the model name. The status becomes `ANSWERED`, the apps show the post with an AI label and its sources, and staff accept or ignore it like any other answer. The question stays open until staff close it.

`POST /api/courses/{id}/rag/compare` runs the same retrieve and generate steps for a staff user with all five settings in the request and writes nothing. That is the endpoint the T6 harness calls.

## Design Process (Elephant/Goldfish)

**Elephant.** On 2026-10-19 I ran the Elephant as one long-lived subagent that I kept talking to across the whole design phase ([session 1e0b939f](../ai_log/2026-10-19_21-10-14_1e0b939f.md) and the hand-backs after it). Its first phase only read: the thread model, access control, accept/close, the harness and where RAG would hook in, plus a check online of the Infinity and gte-Qwen2 facts that the design depended on (Infinity has no last-token pooling option of its own; it takes pooling from the model's own config, which for gte-Qwen2 is last-token). Only then did it write the first [`docs/design-rag.md`](design-rag.md) (`85eca8d`). That draft was about 12,600 words and very detailed on the happy path: data model, citations per chunk type, profiles versus per-request settings, the compare contract.

**Goldfish.** A fresh subagent then read only the design document, nothing else in the repo, and reported what it understood and what was missing ([2026-10-19_21-41-26](../ai_log/2026-10-19_21-41-26_1e0b939f.md)). It found 11 must-fixes, 15 should-fixes and several scope suggestions. The theme was that the Elephant had designed the success path well and the failure paths badly:

- **Timeouts.** The generation lock was held across embedding and generation, and live board jobs could queue ahead of a compare call, so a harness request could exceed its 180 s limit. The fix was to hold the lock only around Ollama, give compare a 30 s lock wait and then a 503, and add `RAG_LIVE_ENABLED` so the board can be off during eval runs.
- **Data loss on re-sync.** A failed fetch or an empty result would have deleted the good chunks already stored. Now neither deletes anything, and a partial failure rolls back only the job's own additions.
- **Races.** Staff closing a question while the AI job was running was not handled, and nothing said what happens to `PENDING` questions after a restart. Now the insert re-checks the row under a lock and ends `SKIPPED`, and startup marks old `PENDING` rows `FAILED`.
- **The doc was not self-contained.** It relied on `instructions.md` for the T6 requirements, so the reviewer could not check whether the baseline met them. A requirements recap (§1.1) was added.

I made the calls on what to accept. I took all 11 must-fixes, but rejected the suggestion to drop gte-Qwen2 (T6 requires it) and to drop zip upload (it is the repository fallback), and kept semantic chunking only for syllabus and schedule prose, where topics shift inside a section. The Elephant revised the doc to about 9,300 words (`c647565`), and §13 of the design doc records every finding and what changed.

I ran the same loop again on 2026-10-25 for the evaluation plan ([2026-10-25_12-40-17](../ai_log/2026-10-25_12-40-17_1e0b939f.md), [12-47-03](../ai_log/2026-10-25_12-47-03_1e0b939f.md)): I asked for changes that would get the most credible threshold, abstention, hit-rate and timing numbers, then had a fresh Goldfish check each change against `eval/compare_harness.py` for side effects. That review caught real problems with my own proposals. Calibrating through `/rag/compare` at threshold 0 would have run about 56 generations on the VM, float rounding at a 0.05 step boundary could lose a question, and warming the model before our run would have made our timings better than the graders' cold re-run. §14 lists what was kept, modified or dropped.

**Did it change how I implemented?** Yes, a lot. I kept the pattern for every milestone: write `docs/plan-mN-*.md`, have a fresh subagent review the plan, write the tests first, implement, then have another fresh subagent review the diff. Each plan has a "Goldfish plan review" and "Goldfish diff review" section with how each finding was handled. These reviews kept finding things I would otherwise have found on the VM: in M1, that the Chroma image has no `curl` for a healthcheck, that Infinity is amd64-only on my arm64 laptop, and that the design's Compose project name would have orphaned our existing MySQL volume. The design doc also worked as the contract between us: varikooty built the staff pages against §6 before my routes existed, and I answered varikooty's six open questions by updating §6 rather than replying in chat. The cost was time: the design phase took an evening and every milestone carried two extra reviews, but I almost never had to redesign something after writing the code.

## RAG Configuration Findings

**What I planned.** I wrote the evaluation plan in design §11: a baseline of the `sliding-window` profile, `all-MiniLM-L6-v2`, a calibrated threshold, the T5 guardrail prompt and `qwen2.5:1.5b`, with one-factor-at-a-time comparisons on all five axes (type-tailored chunking; gte-Qwen2 with last-token pooling; threshold ± 0.15; `cite-every-claim` and `resist-injection` prompts; `qwen2.5:3b`). The plan fixed the rules before any run:

- the threshold is calibrated from retrieval scores alone, as the lowest value above the out-of-scope question's best score that keeps every in-scope question whose expected source is retrieved;
- a comparison beats baseline on retrieval only if its hit rate is higher **and** its no-match accuracy is not lower, so the permissive threshold cannot win just by answering the question it should refuse;
- a one-question difference is a tie, since hit rate rests on about 11 scorable questions and no-match accuracy on one;
- timing is reported as a median over matched rows with the max beside it, because abstained rows count as 0 ms and the first call after a model switch pays the model load.

varikooty turned this into [`eval/configs.json`](../eval/configs.json) and the ingest script, and the [varikooty write-up](varikooty.md) lists each comparison with its expected effect.

**What the evidence showed.** Honestly, there is no harness evidence. The run against the deployment was not completed before the deadline (varikooty's local attempt ended in a disk-full crash, and the VM run depended on the redeploy), so there is no `eval/report.md` and I cannot say which single change made the biggest difference to answer quality or what it cost. I also did not build three parts of my own plan: `calibrate.py`, `eval/preflight.py` and `eval/summarize.py` are described in §11 but do not exist, so the 0.50 threshold is the team's starting value, not a calibrated one.

What I did observe while building M5 is one data point about thresholds. In the integration run ([`docs/plan-m5-pipeline.md`](plan-m5-pipeline.md) §11) the off-topic test question scored below 0.50, so retrieval abstained with `NO_MATCH` before the model was ever asked. That is the behavior the plan wanted for out-of-scope questions, but it is one question, not a measurement.

**Intuition going in.** I expected the threshold to matter most for retrieval and the 3B model to matter most for answer quality, at roughly double the generation time on 4 vCPUs. The reason for the five-axis plan was to check that, because a better generator cannot use a passage that retrieval never returned. I also expected gte-Qwen2 to be hard to judge fairly: its scores sit on a different scale from MiniLM's, so one shared threshold confounds the embedding comparison. That is why §11.2 asked for threshold-free hit@K per profile, which would have separated "retrieves better" from "scores higher". Without a run I can't say whether any of this was right, and I'd rather leave it as a prediction than guess at numbers.

## Best Practices Learned

- **Write the design before the code, then have a fresh reader attack it.** The author of a design, human or AI, checks the happy path. A reviewer with no context checks what the document actually says, and that is where failure paths, races and unstated assumptions show up. I'd use a fresh review of the diff as well as the plan; both caught different things.
- **In a RAG system, put the facts the model must not invent outside the model.** Citations are computed from chunk metadata at ingest time and attached by code, so a wrong or made-up URL is impossible by construction. The same idea applies to status: whether an answer was posted is decided by retrieval scores and a row lock, not by the model's text.
- **Design failure paths explicitly.** Most of the Goldfish findings were about what happens when a fetch fails, a model is missing, a request times out or two things happen at once. A background job that writes to a shared row needs conditional updates and a defined outcome for every status.
- **Decide how you will judge an evaluation before you run it.** The winner rule, the tie rule and the caveat that the threshold is tuned on the test questions were all written before any run, so a result couldn't be argued into a win afterwards. The other half of the lesson is that a plan is not a result: the evaluation needed to run on the VM days before the deadline, and planning more tooling did not substitute for running it.
- **Local model serving is a capacity problem first.** Memory limits, model sizes, CPU-only generation times and one-model-at-a-time loading decided which configurations were practical and how timings should be measured. Pin versions and verify the serving APIs (we kept a U1–U10 list of unverified facts and checked them off) before building on them.
- **Split team work by file ownership and keep a written contract.** Because each of us owned whole files, we could work in parallel on separate branches, and API questions were answered by updating design §6, so the frontend and backend never drifted apart.
