  ## 1. What I learned
  
  QnA is a Piazza-style board with no AI today. The feature is a local, CPU-only RAG auto-responder built on three Docker services: Ollama for generation, Infinity for embeddings and ChromaDB for vectors.
  
  **Ingestion.** Staff register resources for a course: a syllabus page, a schedule page, a GitLab repository, or an upload. A historical-Q&A resource is created automatically from the course's accepted or closed threads. A resource is synced into an *ingestion profile*, which is a named pair of (chunking config, embedding model) with its own Chroma collection, `c<course>_p<profile>`. Every profile splits content by its structure first (HTML h1–h3, markdown headings, PDF pages, one chunk per thread). Units that are still too big go to a sliding window or a semantic chunker, with sizes counted in MiniLM WordPiece tokens. Each chunk stores a finished citation URL, computed at ingest time. Re-sync diffs chunk IDs: it adds new chunks, updates metadata on kept ones and deletes stale ones.
  
  **Live answer flow.**
  1. `create_question` commits and returns 201 with `ai_status=PENDING`.
  2. A background task embeds title plus body with the default profile's model and runs a top-4 cosine query.
  3. If no chunk scores at or above `RAG_DEFAULT_THRESHOLD`, the status becomes NO_MATCH.
  4. Otherwise it takes `GENERATION_LOCK`, calls Ollama with the guardrail prompt plus `LIVE_SUFFIX`, and checks the reply for a decline.
  5. It inserts an ANSWER post from a system user with `author_role=AI`. Code, not the model, attaches the citations: a JSON snapshot plus a `Sources:` block in the body.
  6. Staff accept the post through the existing accept endpoint.
  
  **`/rag/compare`** is a staff-only dry run.
  - It takes exactly five fields: question, profile, threshold, prompt and model.
  - It checks the profile (404 if missing, 409 if empty), the Ollama model (422) and the Infinity model (409).
  - It releases the DB connection, then holds `GENERATION_LOCK` while it embeds, retrieves and generates.
  - It returns `matched`, the chunks above the threshold, the raw answer, and timings plus host-wide `cpu_percent`.
  - It writes nothing.
  
  **Profiles versus per-request settings.** Chunking and the embedding model are fixed per profile; you change them by creating a new profile and re-ingesting. Threshold, system prompt and generation model are per request, or come from env vars for the live board.

  ## 3. Critique
  
  **Locking and timeouts are broken.**
  - §4.5.8 claims the worst case is "one in-flight live generation plus its own work". `asyncio.Semaphore` is FIFO, so every queued live job ahead of a compare call runs first. Five questions posted during the eval means up to 5 × 120 s of waiting.
  - Even with a single live job, the sum is 120 s (live generation) + up to 60 s (embed, inside the lock) + 120 s (own generation) = 300 s. That is over the harness's 180 s limit (§3.4).
  - A 504 also aborts the harness. Nothing pauses the live board during eval, and `RAG_ENABLED` is global. Any student or staff question in any course can kill the graded run.
  - Lock waits have no bound.
  
  **Profile `chunk_count` is stale.**
  - §4.5.5 updates it only at the end of a job. §4.5.6 resource deletion never updates it, and the restart sweep doesn't either.
  - Compare's 409 and the live board's SKIPPED path both depend on it. During the first ingest a profile with chunks reads as 0, and after deleting its resources an empty collection reads as non-zero.
  
  **Re-sync algorithm (§4.5.6)**
  - If `content_hash` covers only the display text, a heading rename keeps the ID. The `keep` branch then updates metadata only, which leaves a stale document (the returned `text`) and a stale embedding. Hash the embedded document.
  - An empty or bogus fetch wipes the resource and marks it READY. A wrong subpath, or a GitLab login or 404 page (§4.5.2 says "always parsed as HTML, whatever its Content-Type", with no status check), deletes every chunk.
  - A mid-batch failure (Infinity timeout) leaves new and old chunks coexisting indefinitely. The duplicates crowd a top-4.
  - `update` and `delete` with an empty ID list are unsafe across Chroma versions; in some, a delete with no filter has removed everything. Guard them.
  - Deleting a resource while a job is syncing it re-creates orphan chunks.
  - Sliding windows shift on any early insertion, so the "re-embed nothing" saving only applies when nothing changed. That is fine, but don't oversell it.
  
  **Similarity and threshold**
  - `round(1−d, 4)` happens before the `>=` threshold comparison, so 0.49996 passes 0.50. Compare on the raw value and round only for output.
  - §11.2: "(P+L)/2 rounded down to 0.05" can land at or below P. With P = 0.41 and L = 0.44 it gives 0.40, so q14 matches. Also, the threshold is tuned on the same 14 questions it is graded on; say so.
  - A single threshold across MiniLM and gte (§4.4.6) can make the embedding axis meaningless, with everything or nothing matching. Report each profile's score distribution next to the results.
  - The cosine conversion and the L2 note are correct, but U4 (how cosine space is configured) is still open, and the unit test depends on it.
  
  **Dry-run guarantee**
  - It is enforced only by convention ("never imports `qa_service`"), and the T7 test checks one thread's post count. Strengthen it:
    - assert global row counts for posts, questions, jobs, resources and states;
    - check `ai_status`;
    - check Chroma `count()` per collection;

  - Compare does have a real side effect: with `MAX_LOADED_MODELS=1` it swaps the loaded Ollama model, which slows the live board. It is harmless, but it should be stated.
  - §4.5.1 auto-creates the historical-Q&A resource on *GET* routes. There is no unique constraint, so concurrent GETs create duplicates. Create it in migration or bootstrap, with `UNIQUE(course_id)` for that type.
