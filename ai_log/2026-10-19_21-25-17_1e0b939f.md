  ## (a) Citation data model
  
  **Position:** the full, clickable citation URL is computed **at ingestion** and stored as the `source_url` metadata on each Chroma chunk. Both `/rag/compare` and the live board just read it back.
  
  How each resource type builds its URL:
  
  | Type | URL |
  |---|---|
  | Web page | `{base}#:~:text={start},{end}`. `start` and `end` are the first and last ~5 words of the chunk's *display* text (body text only, without the heading prefix), percent-encoded. The characters `-`, `,` and `&` must be escaped. |
  | Repo markdown | `{repo_web}/-/blob/{commit_sha}/{path}?plain=1#L{a}-{b}`. The SHA makes it a permalink. `?plain=1` is needed because GitLab's rendered markdown view ignores `#L` (unverified on git.doit.wisc.edu). |
  | Repo PDF | `{repo_web}/-/raw/{sha}/{path}#page={n}`. It uses `raw`, not `blob`, because the browser's own PDF viewer honours `#page`. Whether GitLab's pdf.js blob view does is unverified. |
  | Historical Q&A | `{FRONTEND_URL}/student/questions/{qid}` |
  
  **Uploads** need a staff-entered `citation_base_url`.
  - For the eval, set it to the team's own GitLab URL, for example `https://git.doit.wisc.edu/<ns>/qna-74/-/blob/main/eval/sample_data/web/syllabus.html`, or to `.../eval/sample_data/repo/` for the repo zip. The paths inside the zip are appended to it.
  - If the zip has exactly one top-level directory, strip it.
  - The upload UI previews the first resolved URL before ingesting, so a mismatch with the expected path is caught early.
  
  **Chroma metadata per chunk** (flat scalars only; Chroma rejects None and lists, so omit absent keys):
  - `course_id`, `profile_id`, `resource_id`, `resource_type`
  - `source_url`, `title` (heading path or thread title), `rel_path`
  - `line_start` and `line_end`, or `page_start` and `page_end`, or `question_id`
  - `chunk_index`, `content_hash`, `ingest_job_id`
  
  **MySQL holds no chunks.** It holds resources, profiles, jobs and per-(resource, profile) state. I rejected a MySQL chunk table that mirrors Chroma because the dual write drifts.
  
  **The AI post** gets a new nullable JSON column, `posts.citations`. It stores `[{rank, resource_type, title, source_url, similarity_score}]` as an immutable snapshot, plus `ai_model` and `ai_profile` strings for audit.
  - I rejected a `post_citations` table: there are no relational queries to justify it, and it would add another eager load to `_question_load_options`.
  - The citations are also appended to the body as plain-text "Sources:" lines, because bodies render as plain text.
  - Citations are attached by code (the chunks above threshold, deduplicated by URL). The model is not asked to produce them, because small models invent URLs.
  
  **Risks:**
  - A text fragment silently fails if the stripped text doesn't match the rendered text (entities, `&mdash;`, a chunk that crosses elements). Keep the fragment words inside one block element where possible.
  - For eval uploads, a fragment pointing at a GitLab code view of raw HTML will mostly fail. Only live URL resources get fully working fragments.
  - Line numbers drift until the next re-sync; the SHA permalink avoids this.
  - Links to private repos need the user to be logged in to GitLab.

  ## (d) Configuration-driven pipeline
  
  **The ingestion-time half: profiles.**
  - New table `ingestion_profiles` with `(course_id, name)` unique, plus `embedding_model`, `query_instruction`, `chunking` (JSON), `status` and `created_at`.
  - The Chroma collection is `c{course_id}_p{profile_id}`, created with cosine space. On 0.x that's `metadata={"hnsw:space":"cosine"}`; on 1.x it's `configuration`. Check which applies to the pinned version. We pass our own embeddings and use no Chroma embedding function.
  - A profile is **immutable once ingested**. To change chunking or the model, create a new profile.
  - Creating a profile validates the model against Infinity's served models (`GET /models`). An unknown model is a 422.
  - **Chunking uses one fixed tokenizer for every profile**: MiniLM's `tokenizer.json`, vendored in the repo. That way `sliding-window` gives byte-identical chunks under MiniLM and gte, and the embedding comparison isolates only the model. MiniLM truncates at 256 tokens, so the size is capped below that.
  
  Presets:
  
  | Profile | Embedding model | Chunking |
  |---|---|---|
  | `sliding-window` (baseline) | MiniLM | every fallback is a window of 200 tokens with 40 overlap |
  | `type-tailored` | MiniLM | **PDF:** a 120/30 window that resets at page boundaries, because slides are dense with one concept per slide and the ground truth targets slide titles. **Web:** semantic, using sentence units, a similarity threshold of 0.6 (tune it), a 240-token cap and a 200/40 recursive fallback, because syllabus sections are long prose with topic shifts. **Markdown oversized sections:** semantic, same settings. **Q&A:** none. |
  | `embedding-alt` | gte-Qwen2-1.5B | same as `sliding-window` |
  | `bge-small` (optional) | bge-small (CLS pooling via `auto`) | same as `sliding-window` |
  
  **The query-time half.** `similarity_threshold`, `system_prompt` and `generation_model` come per request in compare. The live board reads a new table, `course_rag_settings`, keyed by `course_id`, with `enabled`, `default_profile_id`, `similarity_threshold`, `system_prompt` and `generation_model`. Staff edit it in the UI, and the env `RAG_DEFAULT_*` values seed it.
  
  **Similarity.** Chroma's cosine distance is `d = 1 − cos`, so `similarity_score = 1 − d`, rounded to 4 decimal places. A chunk counts if `similarity_score >= threshold`.
  - Do not leave Chroma's default L2 metric. If someone does, the conversion becomes `1 − d/2` for unit vectors.
  
  **Threshold.** It's not chosen yet. First calibrate by running ground truth at threshold 0 and reading the score distribution (MiniLM relevant hits are typically about 0.4–0.7). The example's 0.65 may be too strict.
  - **Risk:** one threshold shared across embedding models confounds the embedding axis, because gte's score distribution differs. Say so in T10.

  1. **Auth:** `require_course_staff`.
  2. **Validate the body:** `extra="forbid"`, a non-empty question of at most 4000 characters, a threshold in [0, 1], a non-empty prompt, a model tag.

  ## (e) Ingestion
  
  **Resources table.** `course_resources` has:
  - `resource_type`: `ENUM(syllabus, schedule, repository, historical_qa)`
  - `source_kind`: `ENUM(url, upload)`
  - `url`, `git_ref`, `citation_base_url`, `upload_path`
  - `title`, `created_by`, `created_at`
  
  One `historical_qa` resource is auto-created per course.
  
  **State and job tables.** `resource_profile_state` has `(resource_id, profile_id)` unique, plus `status`, `chunk_count`, `last_commit_sha`, `last_synced_at` and `error`. `ingestion_jobs` has `id`, `course_id`, `profile_id`, `resource_id` (null means every resource), `status` (QUEUED, RUNNING, SUCCEEDED, FAILED), `upserted`, `deleted`, `started_at`, `finished_at` and `error`.
  
  **Fetching:**
  - **URL** is the primary path: httpx with a 30 s timeout and a 10 MB cap, https or http only, and a block on hosts that resolve to private or loopback addresses. Without that block, staff could fetch `http://ollama:11434`.
  - **Upload** is the fallback: HTML, MD or PDF files up to 20 MB, or a zip up to 50 MB. Uploads are saved to `uploads_data` so a re-sync can re-read them.
  - **Zip safety:** guard against zip-slip, cap the uncompressed total at 200 MB and 2000 entries, and extract only `.md` and `.pdf` files.
  
  **Repository clone:**
  - Command: `git clone --depth 1 --single-branch [--branch ref] https://host/path.git tmp`.
  - The token is sent as an `http.extraHeader` Basic header of `oauth2:<token>`, passed through `GIT_CONFIG_COUNT`/`KEY`/`VALUE` env vars. It never appears in argv, the URL or `.git/config`.
  - It is attached **only if** the host equals `GITLAB_HOST`, so the token can't leak to an attacker's host.
  - Scrub the token from any stderr we store.
  - `GITLAB_TOKEN` is set only in the VM's `.env`, never in CI variables or the database.
  - Run `git rev-parse HEAD` to get the SHA for permalinks.
  - Walk `.md` and `.pdf` files, skipping `.git` and `node_modules`.
  
  **Structural chunking (both profiles):**
  - **Web:** BeautifulSoup. Drop `nav`, `header`, `footer`, `script` and `style`, then split on h1–h3. The schedule page has one h3 per lecture under h2 week headings. The heading path is prefixed to the embedded text, not to the fragment text.
  - **Markdown:** split on ATX headings, ignoring headings inside code fences. Track a source line for every token, so a windowed sub-chunk still knows its own line range.
  - **PDF:** `pypdf`, page by page. A window that crosses pages records `page_start`, and the citation uses that page.
  - **Historical Q&A:** one chunk per qualifying thread (any post accepted, or the question is CLOSED). The text is the title, the body, then the accepted answer, falling back to the latest STAFF answer. Every profile gets its own copy, because each embedding model is a different vector space. A background upsert into all of the course's profiles also runs after accept or close.
  
  **Re-sync without delete-and-re-add.**
  - The chunk ID is `sha256(resource_id | locator | content_hash)`.
  - Get the existing IDs with `where={"resource_id": rid}`, then upsert only the new IDs. Unchanged chunks skip re-embedding, which matters for gte.
  - After that, delete the stale IDs. There is a brief window where both old and new chunks exist, which is acceptable.
  
  **Run jobs in the background, not inline.** A request returns 202 with the job, the job runs with its own session and the shared semaphore, and parsing runs in `asyncio.to_thread`. Embedding sample_data with gte on 4 vCPUs probably takes minutes (not measured).
